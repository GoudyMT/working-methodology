# Kit Standards

## Kit Standards (How the Methodology Improves) {#kit-standards}

The methodology kit is the baseline every project starts from. These rules keep it current, small and enforced. Each is checked by a machine where one can check it; the check is named. Text the owner wrote or approved word for word (Hard Rule 14 among it) stays word for word, and only the owner edits it; Hard Rule 14 is pinned by a test, and other owner text gets its pin when it is touched.

1. **The kit check runs itself.** `.claude/settings.json` wires `kit-hook.cjs`. Session start: the kit's GitHub ahead of its folder, newer kit rules, kit files this project changed (update skips them), the skills for its cases. Each message: once per kit release made mid-session. Before a compact: rule changes waiting for the kit, the vault backup, plugins past their backup. A failure warns, never stops a session. Why: a check that relies on memory gets skipped. *Check: tests run the hook.*
2. **Rule sort at every closeout.** See "Pre-Compact Scan" step 5b: each rule change is tagged project-only or portable; portable ones go to `/methodology-kit fold-back`, and the owner decides each. Why: methods improve inside projects and are lost unless they flow back.
3. **One home per rule.** A rule lives in one rule module, under one heading with a fixed ID. Memory, notes, briefs and tracking files hold a pointer (`-> rule:<id>`, the fixed ID after the rule's heading), never a restated copy. Why: two copies drift, and the stale one gets followed. *Check: tests flag kit memory lines that repeat this file's wording.*
4. **Briefs read their rules from one source.** Every agent brief tells the agent to read the "Rules every brief carries" item of rule:agent-team-adapter; nobody pastes it. Why: a pasted block goes stale the day a rule changes. *Check: tests read the brief templates.*
5. **Merge and retire at each kit release.** Before a kit version bump, merge overlapping rules, retire rules nothing uses, and keep each module, AGENTS.md and the session-start load under their caps (`kit.config.json` caps), merging inside one module at a time. Every rule carries a one-line why. Why: a standards file that only grows stops being read. *Check: tests enforce the size cap and a why in every rule section.*
6. **A slip that happens twice becomes a guard.** The second time the same mistake happens, the fix is mechanical - a hook, a test, a lint rule or a script check - not more text. The `_Loop Learnings.md` scoreboard records each guard added. Why: text is read when someone remembers to; a guard runs every time.
7. **Trial before standard.** A new kit rule ships marked `[trial]` in the CHANGELOG and listed in the kit's `TRIALS.md`. It becomes standard once a second project has used it cleanly, or when the owner promotes it directly. Why: a rule proved in one project may only fit that project.
8. **Skills by case.** The kit's `.claude/kit/skill-cases.json` maps each kind of task to the skills it loads. Each project turns its cases on in `.claude/skill-cases.local.json`; the session-start hook lists those skills. At most two skills per unit of work; design-time, motion and review-time sets stay apart. A rarely used plugin is a **standby plugin**: off in the Claude config folder's settings, named on its case (`plugin`), and switched on per project in `.claude/settings.local.json`; session start says how when a turned-on case needs one that is off. Why: the right skill unused is no skill, and too many dilute each other. *Check: tests confirm every named skill exists.*
9. **Credit and keep a safe copy.** Each third-party plugin or skill is credited (author, source, license) in `vendor/CREDITS.md` and kept as a pinned backup once its license allows. Read a community skill before first use. Upstream changes enter only through a reviewed `snapshot` and kit bump. Why: credit is owed, and a skill gone upstream must not take the method with it. *Check: tests confirm every backup is credited.*
10. **Back up the vault.** A project's private, gitignored notes (its vault) go to a separate private repo at every pre-compact (`.kit/vault.json`; secret files never copied). The hook commits locally; pushes wait for the owner's yes. Why: an untracked folder is one disk failure from gone. *Check: tests prove secrets are never copied and nothing is pushed.*
11. **One source, written out per tool.** Rules are edited only in the kit's `rules/` (plain Markdown with neutral frontmatter: id, load, paths, when, tags); `kit.mjs build` writes each tool's files - today Claude Code's `AGENTS.md`, `.claude/rules/` and `standards/`. Each tool's output names the docs it follows and is re-checked against them at every kit release. Why: one tool-neutral source lets any AI use the rules, and a hand edit to a written-out copy is overwritten. *Check: the build-freshness test.*
12. **Improvement reports, one format.** A process or method gap found while using the kit (a step in the wrong order, a rule that misled, a check that did not run) is written up the session it shows up: `node .claude/improvement-report.mjs new "<title>"` starts `.kit/reports/IR-<date>-<slug>.md` from the kit template, and `audit` must PASS before the owner hands it to the kit as is. Every cause carries evidence and says proven or guess; every fix says where in the kit and that its standards effect is same or higher - a change that would lower one goes under "Decisions for the owner", never as a fix. The kit closes a report by naming it in the CHANGELOG line of the release that fixes it, and sets its Status and Closed by; `/methodology-kit status` lists the ones still open. The kit's own example is `.claude/kit/improvement-report-example.md`. Why: an improvised write-up is hard to compare and easy to lose, and a fix that quietly lowers a standard is the gap this kit exists to close. *Check: tests run the audit on the example and on each fault it must catch.*
13. **A missing kit is a full stop** (the owner, 2026-10-31). `kit.mjs install user` wires a gate (`kit-gate.cjs`) into the Claude config folder's `settings.json`: in a folder with no kit install record, every prompt is refused with the fix, except a prompt that installs it; a folder may opt out with `.kit/no-kit`. A project's own hook refuses every prompt when the active config folder (`CLAUDE_CONFIG_DIR`, else `~/.claude`) has no kit. A config folder with no kit at all runs no gate, so each new one gets `install user` first. Why: the kit flow is how all work here is done; a session that runs without it believes it is covered. *Check: tests run both gates.*
14. **Context budget.** Two costs are weighed for every addition: *context load* (text in every session - the core, memory index, global CLAUDE.md, skill and plugin listings) and *cognitive load* (what the owner must remember). Every always-loaded line earns its place or moves to an on-demand module, a script or a pointer; a pointer names its trigger first ("before a PR: rule:pr-body"); each plan step ends on a done-condition that can be checked; one term per idea, listed once in the project glossary when a project keeps one. `kit.mjs measure --real` counts what actually loads, and `/methodology-kit status` shows it against its cap. Why: a kit that only grows costs every session more and is followed less. *Check: tests run measure --real.*
15. **Team decisions go out as a questionnaire.** When a decision needs people beyond the owner, it goes as `.claude/kit/team-questions.md`: most important question first, each answerable in a word with one short line per option and a recommendation, the deadline and who decides on a tie. Why: async teams answer a short ranked list; they skip a long thread.
