# Changelog Entry Template

> One entry per release in `CHANGELOG.md`, newest first, grouped the Keep a Changelog way (Added, Changed, Fixed, Security, Removed, Deprecated). One line per change, what a reader of the release gets; the detail stays in the PR body. Leave out a group with nothing in it. Version and date as in the VERSION file and the tag.

```md
## <x.y.z> - <YYYY-MM-DD>

<One sentence: what this release is for.>

### Added
- <a new thing a person can do or rely on>.

### Changed
- <what works differently now, and the one thing to do about it if any>.

### Fixed
- <the bug, as the person met it>.

### Security
- <the hole closed, at the level a reader may know; an unfixed one is never described>.

### Removed
- <what is gone, and what to use instead>.
```

Rules of thumb: about 12 words a line; no file names unless the reader edits that file; no counts of tests, findings or commits.
