How a new rule travels

When we find a better way to work in one project (a format, a skill, a tool or a check), this is the route it takes into the shared kit, and from the kit into every other project.

Works today The owner decides

The route

1We find a better way

During work in a project. Saved at once to that project's standards; notes point to it.

today
2Rule sort

At each pre-compact, every new rule is tagged "this project only" or "every project".

today
3Kit report

A hook runs fold-back in report mode before the compact: "N rules waiting for the kit".

hook, today
4The owner decides

Each rule, one at a time: general (goes to the kit) or project detail (stays).

owner's yes
5Kit release

Written into the kit without project details, tested, version bumped. New rules start as a trial. Pushed only on the owner's go.

today
6Every project catches up

A hook at session start: "kit has N newer rules, run update". New projects start from the latest kit.

hook, today

6 feeds back into 1: a project that pulls the update keeps working, finds the next improvement, and the loop repeats.

The three places a rule can live

Your global setup

~/.claude/CLAUDE.md, ~/.claude/skills, ~/.claude/agents
  • Coding and communication standards
  • Skills such as agent-team-build and human-factor
  • Agent roles: builder, checker, orchestrator
Reach: every project, at once.

One project's rules

_Working Standards.md, CLAUDE.md, AGENTS.md, project notes
  • Its privacy and legal limits
  • Its size budgets and full gate
  • Its restrained UI and motion style
Reach: this project only. Private files, never pushed.

The methodology kit

kitDir from ~/.claude/kit-install.json
  • The general version of every rule
  • Templates, tools, skills, hooks
  • Versioned, tested, released on your go
Reach: every project that runs update, and every new project.
The gap this closes. Fold-back and update existed, but nothing ran them on their own, so a rule reached the kit only if someone remembered. Steps 3 and 6 make the reminder automatic. The kit installs both hooks, the rule sort and the items below into every project, so none of it can be skipped by mistake.

Six safeguards that keep the system healthy

SafeguardWhat it preventsStatus
Backup of private files
The project's private standards, plans and notes go to a private GitHub repo at each pre-compact, on the owner's go.		Losing every decision if one disk fails.today
One home per rule
A rule lives in the standards file; notes only point to it.		Two copies drifting apart.today
Merge and retire
Each kit release merges or removes old rules under a size cap; every rule says why.		A rulebook too long for anyone to read.today
Twice means a guard
A slip that repeats becomes a hook or a test.		The same mistake coming back despite a written rule.today
One source for agent rules
Briefs pull the rules block from one file.		Agents working from an old copy.today
Trial before standard
A new kit rule becomes standard after a second project uses it cleanly.		One project's bad idea reaching every project.today

The session-start check also lists files the update skipped because a project changed them, so no project drifts quietly.

Credit where it is due

A credits file lists every community skill we use: name, author, source and license. The kit's tests fail if a skill is in use without its entry.

A safe offline copy

  • Each community skill is read and reviewed before first use.
  • A pinned copy lives in the kit, where its license allows it.
  • Work never depends on a remote plugin that could change or go offline.
  • An update arrives only through a reviewed kit release.
